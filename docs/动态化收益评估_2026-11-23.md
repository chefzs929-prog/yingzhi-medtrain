# 动态化收益评估

> 结论：**只有「课堂数据多端同步」这一块值得动态化，其余都不划算。**
> 因为同步的前端骨架已经写完，缺的只是两个后端端点；而账号、内容在线编辑、
> 数据库化这些"更动态"的部分，收益低于它们带来的运维与合规成本。
>
> 评估日期：2026-11-23｜方法：代码核查 + 场景推演（量化部分为估算，已标注）

> **决策（2026-11-23）**：D1 已实施——主服务内置 `/api/snapshot` 与 `/api/merge`，
> 服务端合并、原子写、备份、跨进程锁、可选口令；D2–D4 转入 [未来规划.md](未来规划.md)。

---

## 1. 「动态」在这个项目里有四层含义

| 层级 | 含义 | 现状 |
| --- | --- | --- |
| D1 数据动态 | 课堂/作业数据在设备间实时同步 | 前端已完成，**后端缺失** |
| D2 身份动态 | 账号、登录、角色与权限 | 无，靠班级码 + 姓名 |
| D3 内容动态 | 题库/病例在线编辑、审核、即时生效 | 无，改内容要重新构建部署 |
| D4 分析动态 | 学习数据看板、班级统计 | 本地计算，无跨设备汇总 |

「Agent 动态」不在此列——上一轮已用隧道解决，且 Agent 本来就该跑在本机。

---

## 2. 现状：静态到什么程度

| 项 | 现状 | 动态化的边际 |
| --- | --- | --- |
| 站点 | 纯静态 10 MB，构建后推 gh-pages | 无需改 |
| 知识库 | JSON 构建期打包，内存检索 | 无需改 |
| 课堂数据 | `localStorage`，单浏览器 | **D1 的核心缺口** |
| 跨设备 | 手动「导出 JSON → 发送 → 导入」 | **D1 的核心收益** |
| 同步前端 | [classroom-sync.js](../kb/app/classroom-sync.js) 已实现 pull/push/merge/离线回退 | 只需后端 |
| 后端端点 | 无 `/api/snapshot`、无 `/api/merge` | 缺 2 个端点 |
| 数据库 | 无任何数据库依赖 | JSON 文件足够 |

也就是说：**D1 不是从零做，是补最后一公里。**

## 3. 收益分级

| 方案 | 收益 | 成本 | 风险 | 建议 |
| --- | --- | --- | --- | --- |
| **D1 课堂同步后端** | 高 | 1–2 天 | 中（并发、隐私） | **做** |
| D2 账号体系 | 中低 | 3–5 天 | 高（合规、找回、注销） | 不做 |
| D3 内容在线编辑 | 中低 | 3–5 天 | 中（审核流缺失） | 不做 |
| D4 学习分析看板 | 中 | 2–3 天（依赖 D1） | 低 | D1 之后再说 |

## 4. 为什么只有 D1 值得做

**论据一：痛点是真的，且现在就在付代价。**
教师收作业的现行流程是：学生导出 JSON → 发给教师 → 教师逐个导入
（[classroom.js](../kb/app/classroom.js#L1338)）。每份 1–2 分钟，30 人班就是 30–60 分钟/次，
而且中间任何一步出错都要重来。

**论据二：投入产出比极高。**
前端已经具备 pull/push/客户端合并/900ms 防抖/离线回退
（[classroom-sync.js](../kb/app/classroom-sync.js#L80-L125)），后端只需：
`GET /api/snapshot` 返回快照、`POST /api/merge` 合并写回。现有 `main.py` 零新依赖即可承载。

**论据三：其余三层的收益撑不起成本。**

- **D2 账号**：班级码 + 姓名已经能区分学生。加账号不解决教学问题，只增加密码找回、注销、
  数据归属这些运维负担；而学生真实姓名上云，直接引入合规问题。
- **D3 内容在线编辑**：题库一年改几次，改一次重新构建 2 分钟。为了省这 2 分钟引入编辑器、
  审核流、版本回滚，不划算；而且本项目的内容红线恰恰依赖"构建期固定 + 审计"。
- **D4 看板**：价值成立，但它只是 D1 的下游——数据能汇总了，统计自然能做。顺序上不该先做。

## 5. 收益量化（估算）

假设一个 30 人班、每次课 2 份作业、一学期 16 次课：

| 项 | 现在 | D1 之后 | 节省 |
| --- | --- | --- | --- |
| 收作业（教师） | 30–60 分钟/次 × 32 次 ≈ 16–32 小时 | < 1 分钟/次 | **约 15–30 小时/学期** |
| 学生换设备 | 进度丢失，需重做 | 自动恢复 | 不可估但真实 |
| 教师看进度 | 看不到，只能等收齐 | 实时可见 | 提前发现掉队 |
| 数据丢失 | 清缓存即全丢 | 服务端留档 | 风险归零 |

> 估算基于"每份导入 1–2 分钟"的现行流程，实际耗时取决于操作熟练度。

单人演示、单机课堂（学生轮流用同一台电脑）场景下，D1 收益接近 0——这是唯一不该做的场景。

## 6. 最小动态化方案（D1）

**后端**（复用 `yingzhi/serve/main.py`，零新依赖）：

1. `GET /api/snapshot` → 返回 `data/classroom.json`。
2. `POST /api/merge` → **服务端合并**，不能整体覆盖。
3. 写入用「临时文件 + 原子替换」，保留上一版备份。
4. 可选 `X-Sync-Token`，防止公网被随意读写。

**必须解决的一个技术点：并发覆盖。**
当前 `push` 发送的是整库，若服务端直接覆盖，两个学生同时提交会丢一个。
服务端需按 `id` + `updatedAt` 合并（与前端 `mergeInto` 同规则），或引入版本号做乐观锁。
这是 1–2 天里最需要认真做的部分，也是最容易埋雷的部分。

**前端**：不改代码。已有「同步设置」入口，填服务地址即生效；无服务时自动回退本机模式。

---

## 7. 隐性代价

| 代价 | 说明 |
| --- | --- |
| 失去"零运维" | 服务要一直在线，否则同步失败（但有离线回退，不会白屏） |
| 失去"断网可用"的一部分 | 跨设备能力依赖网络；单机能力保留 |
| 隐私 | 学生姓名 + 作答记录上云，建议默认用学号/昵称 |
| 调试复杂度 | 从"改文件即生效"变成"要排查服务端状态" |

---

## 8. 明确不做

- 不做账号体系（班级码 + 姓名够用，且避免合规负担）。
- 不引入数据库（单班数据 < 1 MB，JSON 文件 + 备份足够）。
- 不做内容在线编辑（构建期固定 + 审计是当前的质量保障）。
- 不把静态站点整体改成 SSR/CSR 框架（10 MB 静态站秒开、可离线，是优势不是包袱）。
