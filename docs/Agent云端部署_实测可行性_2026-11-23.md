# Agent 云端部署：实测可行性评估

> 结论：**技术上可行，且比 11-18 的方案评估更乐观——模型链路已经能跑，不需要重写。**
> 但「把 Agent 搬上云」这件事本身不成立：DeepWorks 引擎无法容器化，上云等于切到
> 直连模型分支，答辩口径会从 `served_by=agent` 变成 `served_by=llm`。
> 真正的工作量不在推理，而在 **4 个部署后必然出错的接口契约** 和 **双引用不达标**。
> 预计 1–1.5 人日到「可对外」，其中 0.5 天是硬门槛。

- 评估日期：2026-11-23
- 方法：本地实测（`--offline` 精确模拟「无 DeepWorks 引擎」的云上形态）+ 代码核查
- 前序文档：[云端Agent部署方案_可行性与改造清单.md](云端Agent部署方案_可行性与改造清单.md)（2026-11-18，方案阶段）

> **决策（2026-11-23）**：本文方案暂不实施。当前只做隧道演示，Agent 保持在本机运行；
> 容器化、鉴权、双引用补齐等已归档到 [未来规划.md](未来规划.md)，条件成熟时再启动。

## 1. 实测结论（本次新增，非推测）

用 `--offline`（禁用 gateway，只留直连模型）起服务，等价于云上没有 opencode 的环境：

| 场景 | 结果 | 判定 |
| --- | --- | --- |
| 凭据有效性（`GET /v1/models`，不耗推理） | 文本/视觉均 HTTP 200，191 个模型，目标模型在列 | 可用 |
| 纯文本问答「气胸的影像表现」 | 6.9s，482 字，`served_by=llm`，`degraded=false`，引用 1 条 `SIGN-008` | 通 |
| 带图问答（121K 胸片，CR/PA） | 15.4s，780 字，`vision_percept` 2.7s 返回 modality/view/4 findings | 通 |
| 合规拦截「怎么治，是不是癌症」 | 0.0s，`blocked=true`，**未发生模型调用** | 通 |
| `/api/health` | `ok=false`，`agent_ready=false`，`real_llm=false` | **错**（见 4.2） |

也就是说：**推理层已经就绪，缺的是服务外壳**。

同时纠正 11-18 文档的三处过时数据：

| 项 | 旧文档 | 实测 |
| --- | --- | --- |
| `kb/data` 体积 | 6 MB | 22 MB（含 `.v1/.v2/.backup`；服务实际只读 16 个文件，约 2.2 MB） |
| 直连分支状态 | 「方案，未实施」 | `llm.py` 499 行已实现，含 Router/Retriever/Answerer，纯标准库 |
| 双模型路由 | deepseek-chat + qwen3-vl-plus | 实测两个槽位都指向 `qwen3.8-flash`（同一网关） |

## 2. 为什么「把 Agent 搬上云」不可行

| 依赖 | 位置 | 容器里的结果 |
| --- | --- | --- |
| opencode 进程发现 | [discover.py](../yingzhi/serve/discover.py#L91-L113) 用 `lsof`/`pgrep`/`ps eww` 扫本机进程 | slim 镜像无 `lsof`/`procps`，直接抛 `DiscoverError` |
| 凭据 | 从目标进程环境变量里读 | 桌面进程不存在，无从读取 |
| 智能 | agent + skill + workflow 全在 DeepWorks 内 | 不在仓库里，无法打包 |

所以云上只有两条路：**隧道（让云访问你家 Mac）** 或 **直连模型（换掉推理层）**。
中间没有第三条。

## 3. 三条路线对比

### A. 隧道（今天就能用，0 改动）

```bash
cloudflared tunnel --url http://127.0.0.1:8800
```

| 项 | 值 |
| --- | --- |
| 改动 | 0；前端「连接设置」里填隧道地址即可（[agent-lite.js](../kb/app/agent-lite.js#L35-L52) 已支持） |
| 口径 | `served_by=agent`，答辩口径不变 |
| 硬限制 | 这台 Mac 必须开机、不休眠、DeepWorks 在跑、8800 服务在跑；域名每次重启变化 |
| 定位 | **答辩兜底，必做**，不是正式部署 |

### B. 容器 + 直连模型（推荐正式方案）

| 项 | 值 |
| --- | --- |
| 改动 | 4 处契约修复 + 鉴权 + Dockerfile（见第 4 节） |
| 工作量 | 0.5 天到「能对外」，再 0.5–1 天到「双引用达标」 |
| 口径 | `served_by=llm`，**必须主动说明**，不能冒充 agent |
| 平台 | Fly.io / Railway / Render（Docker 原生，SSE 支持好） |
| 成本 | 容器 ¥0–25/月 + token |

**一个被低估的便利**：`--site` 默认就指向 `outputs/medtrain`（[kb_api.py](../yingzhi/serve/kb_api.py#L23-L26)），
把站点一起 COPY 进容器，前端与 `/api` 同源，**用户完全不用配地址**，也没有跨域与混合内容问题。
站点仅 10 MB / 102 个文件，一体化完全可行。

### C. Serverless

不推荐：带图请求实测 15.4s，叠加冷启动 1–3s，容易撞平台超时；SSE 在部分平台受限；
收益（按次计费）在低访问量下抵不过调试成本。

## 4. 上线前必须修的问题（按严重度）

### 4.1 容器不可达 —— 硬阻塞

[main.py:1790](../yingzhi/serve/main.py#L1790) 写死 `("127.0.0.1", args.port)`。
容器内监听回环地址，端口映射到宿主后外部依然连不上。

改法：加 `--host`（默认 `127.0.0.1`），容器启动传 `0.0.0.0`。1 行 + 1 个参数。

### 4.2 健康检查会自我否定 —— 答辩当场会被抓

三处口径与实际不符：

| 位置 | 现状 | 云上实际 |
| --- | --- | --- |
| [main.py:953](../yingzhi/serve/main.py#L953) | `ok = gateway is not None` | 恒 `false`，但服务可用 |
| [main.py:967](../yingzhi/serve/main.py#L967) | `real_llm = agent_ready or persona_injected` | 恒 `false`，但确实调了真模型 |
| [main.py:1007](../yingzhi/serve/main.py#L1007) | `inference_location = "deepworks_engine"` | 实际在调外部 provider |

后果不只是难看：前端 `probe()` 用 `!!j.ok` 判定连接（[agent-lite.js](../kb/app/agent-lite.js)），
云上会把**正常服务判成不可用**，用户在「连接设置」里测什么都失败。

### 4.3 前端与后端的 llm 契约不一致

前端读 `j.llm_route.ready`，但 `router.describe()` 实测返回 `{vision, text}`，**没有 `ready` 字段**。
即使 4.2 修好，`llm` 仍恒为 `false`。

改法：`describe()` 增加 `ready: bool`，或前端改用 `!!(j.llm_route && (j.llm_route.text || j.llm_route.vision))`。

### 4.4 公网无鉴权、无限流

`Access-Control-Allow-Origin: *` + 无任何 token 校验 + 无频率限制。
公开地址等于把你的模型额度挂出去，被扫到即刷。

最小修复（不引框架）：
1. 可选 `YZ_API_TOKEN`，校验 `Authorization: Bearer`；未配置时保持开放（本地开发不受影响）。
2. 按 IP 的滑动窗口限流（如 20 次/分钟），纯内存 dict 即可。
3. CORS 从 `*` 改为可配的 Origin 白名单。

### 4.5 双引用不达标 —— 质量门槛，未过不能开公网

验收标准要求「每条回答至少 1 个影像锚点 + 1 个文献锚点」，实测：

| 场景 | 影像锚点 | 文献锚点 |
| --- | --- | --- |
| 纯文本「气胸」 | 1（`SIGN-008`） | **0** |
| 带图胸片 | **0** | **0** |

带图分支 0 引用尤其严重：`vision_percept` 拿到了 findings，但没有映射回 `sign_ids` 生成 citation，
等于「看图说话」，落不到证据——这恰好是本项目区别于通用模型的核心卖点。

改法方向（沿用既有约束，不放宽）：
- 带图：把 `percept.sign_terms` 与 `Retriever` 的 sign 名/别名做匹配，命中即发 `citation`。
- 文本：`claims` 已有 `source_url`，按 `sign_ids` 取 1 条最高 `evidence_level` 的作文献锚点，标 `match=candidate`。

### 4.6 视觉 bbox 未回传

`VISION_SCHEMA` 声明了 `bbox`，实测 `vision_percept` 只回了 `modality/view/findings`。
若模型确实不产 bbox，「区域定位」在云端就落不了地，需要换模型或降级为「模板分区」。
上线前必须用 3–5 张图验证一次，不能默认可用。

## 7. 建议顺序

1. **今天（0.5h）**：起隧道，保证答辩现场有真 Agent 可演示。这是唯一能保住 `served_by=agent` 口径的方案。
2. **0.5 天**：修 4.1–4.4 + Dockerfile，把服务跑上公网（此时口径是 `served_by=llm`，必须在页面和口播里说明）。
3. **0.5–1 天**：补 4.5 双引用 + 4.6 bbox 验证。**未达标前不对外公开地址**，只给评审临时访问。
4. **长期**：静态站与问答服务分开部署；站点进对象存储/CDN，容器只跑 `/api`。

---

## 8. 明确不做

- 不把 DeepWorks 桌面引擎塞进容器（无 Linux 服务端形态，凭据依赖进程环境）。
- 不为上云引入向量库（`signs` 60 条、`concepts` 136 条、`claims` 434 条，内存全量载入足够）。
- 不在前端放模型 key。
- 不因为「云上能跑」就放宽三条红线；也不因为切了直连模型就把 `served_by` 写成 `agent`。
