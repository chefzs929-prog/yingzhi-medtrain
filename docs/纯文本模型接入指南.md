# 纯文本模型接入指南

目标：把 `/api/ask` 从「本地关键词兜底」换成「真模型 + 库内检索」，先只做文本，不碰图片。

验收标准不是「模型能说话」，而是这三条同时成立：

1. `/api/health` 里 `llm_route.text` 有值，且不是 `None`。
2. 问「磨玻璃影在 CT 上怎么描述？」，回答是四段式，且 `依据` 段里的 id 能在 `kb/data/signs.jsonl` 查到。
3. 74 条历史提问回放后，四段式齐全率 ≥ 90%，编造 id 为 0。

---

## 第 0 步：先看清现状

不配 key 时服务也能跑，只是走本地规则：

```bash
curl -s http://127.0.0.1:8800/api/health | python3 -m json.tool | grep llm_route
# "llm_route": null
```

`null` 就代表「没有模型可用」，此时 `/api/ask` 走 `fallback_answer()`，界面上显示「本地计算 · 未调用 Agent」。这是设计内的降级，不是故障。

---

## 第 1 步：拿一个 key

只做文本，**不需要多模态**。任何 OpenAI 兼容接口都行：

| 平台 | base URL | 常用模型 |
| --- | --- | --- |
| DeepSeek | `https://api.deepseek.com/v1` | `deepseek-chat` |
| 阿里百炼 | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-plus` |
| 智谱 | `https://open.bigmodel.cn/api/paas/v4` | `glm-4-plus` |

以 DeepSeek 为例：注册 → 控制台 → API keys → 创建 → 复制那串 `sk-` 开头的字符串。

**key 只出现一次，页面关掉就看不到了，先粘到临时文件里。** 不要直接粘到聊天窗口或代码里。

## 第 2 步：写配置文件

```bash
cd /Users/fz/Desktop/黑客松
cp yingzhi/serve/env.example yingzhi/serve/.env
```

编辑 `yingzhi/serve/.env`，只改这一行：

```bash
git check-ignore -v yingzhi/serve/.env

```

有输出就说明被忽略了。

## 第 3 步：启动并自检

```bash
yingzhi/serve/start.sh
```

预期输出：

```
已读取 yingzhi/serve/.env
文本模型：deepseek-chat
视觉模型：未配置（走文本兜底）
RadioCheck 动态层已启动：http://127.0.0.1:8800/
```

**「视觉模型：未配置」是正确的**，说明现在是纯文本模式。

另开一个终端自检：

```bash
curl -s http://127.0.0.1:8800/api/health | python3 -c "
import json,sys
d=json.load(sys.stdin)
print('llm_route =', d['llm_route'])
"
```

预期：

```
llm_route = {'vision': None, 'text': 'deepseek-chat'}
```

如果还是 `None`，说明 key 没读到。检查两件事：`.env` 里有没有多余空格或引号；`start.sh` 是不是在仓库根目录执行的（它自己会 `cd`，但 `.env` 路径是相对仓库根写的）。

## 第 4 步：手动问一条

先别开页面，用 curl 看原始返回：

```bash
curl -sN -X POST http://127.0.0.1:8800/api/ask \
  -H 'Content-Type: application/json' \
  -d '{"query":"磨玻璃影在CT上怎么描述？"}'
```

你会看到 SSE 流，重点是三类事件：

```
event: trace
data: {"stage":"kb_retrieve","detail":{"route":"text","model":"deepseek-chat","signs":1,"claims":8}}

event: delta
data: {"text":"结论：磨玻璃影表现为..."}

event: citation
data: {"id":"SIGN-001","type":"sign","hash_ok":true}

event: done
data: {"degraded":false,"total_ms":4210,"cited":1,"unverified_citations":[]}
```

逐项核对：

- `route` 是 `text` → 走对了分支。
- `signs` 不是 0 → 检索命中了。**如果 `signs: 0`，后面模型再流畅也是在编。**
- `unverified_citations` 是空数组 → 没有编造 id。
- `degraded` 是 `false` → 真的调了模型，不是降级。

## 第 5 步：回放历史提问

单条能过不算数。`yingzhi/run/` 里有 77 个真实 run（去重后约 74 条提问），是之前真实用户问的，比临时编的问题更能暴露问题。

```bash
python3 yingzhi/serve/replay.py --limit 10
```

先跑 10 条看趋势，别一上来全跑（每条 3–10 秒，全跑要几分钟，也费 token）。

确认没问题再全跑：

```bash
python3 yingzhi/serve/replay.py
```

输出：

```
回放 74 条 → yingzhi/replay/20261119-002000
  [1/74] 磨玻璃影在CT上怎么描述？  4210ms 四段齐
  [2/74] 磨玻璃影  3802ms 四段齐
  ...
汇总：成功 74/74，四段齐 70，带引用 61，降级 0，均 4300ms
报告：yingzhi/replay/20261119-002000/report.md
```

回放请求会带 `chain: "replay"`，脚本下次收集时会跳过它们，不会越跑越多。产物在 `yingzhi/replay/`，已 gitignore。

## 第 6 步：怎么读这份报告

打开 `report.md`，只看四个数字：

| 指标 | 及格线 | 不达标说明什么 |
| --- | --- | --- |
| 四段式齐全 | ≥ 90% | prompt 没被遵守，或输出被 `max_tokens` 截断 |
| 带引用 | ≥ 70% | 检索没命中，模型在凭空讲 |
| 编造 id（`unverified`） | **必须 0** | 引用校验漏了，这是红线问题 |
| 平均耗时 | < 15s | 超时或限流，看是不是并发打爆了 |

然后看「明细」表里 `四段` 列为「缺」的行，点进「正文」看它缺哪一段。缺 `依据` 通常是检索为空；缺 `边界` 通常是模型话没说完就被截断。

表里还有一类「合规拦截」：问题里出现「怎么治」「手术」「确诊」这类词时，服务在调模型**之前**就返回固定话术，不参与四段率统计。回放里看到拦截不是失败，是边界生效了。

**最需要警惕的是这种组合：四段齐全 + 引用 0。** 格式对、内容空，模型在用通识补位。看正文里有没有「库内未覆盖」——如果有，说明检索没命中，问题在检索不在模型。

## 第 7 步：按报告调参

三个地方，按命中率从高到低排：

**1. 检索（最常见）**

[llm.py](yingzhi/serve/llm.py#L115) 的 `Retriever.search()` 是**子串匹配**：词条名或别名出现在问题里才算命中。所以「肺上有个磨玻璃影怎么办」能命中，「这个白白的影子是什么」命中不了。

回放里大量 `signs: 0` 就是这个原因。想改的话，在 `search()` 里加一层同义词归一化（把「白白」「发白」映射到「密度增高」这类词条别名），比换模型有效得多。

**2. prompt**

[llm.py](yingzhi/serve/llm.py#L31) 的 `SYSTEM_PROMPT`。如果四段式经常缺，把「输出必须严格四段」改得更硬，或者给出一个完整的示例回答。改完必须重跑回放，不能凭感觉。

**3. 生成参数**

[llm.py](yingzhi/serve/llm.py#L152) 的 `Client.chat()` 里 `max_tokens=900`、`temperature=0.2`。900 对四段式够用；如果正文经常在 `依据` 中途断掉，加到 1200。温度别动，医学内容不需要发散。

## 常见故障对照

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `llm_route: null` | key 没读到 | 检查 `.env` 路径与空格；用 `env` 看进程里有没有 `YZ_LLM_` 变量 |
| 全部回答 `degraded: true` | 上游不可达 | `curl --max-time 10 https://api.deepseek.com/v1/models -H "Authorization: Bearer sk-xxx"` 单独测通 |
| 报 `HTTP 401` | key 错或已失效 | 控制台重新生成 |
| 报 `HTTP 402` | 账户余额不足（key 本身有效） | 充值后重试；`smoke_llm.py` 会原样打印 `Insufficient Balance` |
| 报 `HTTP 429` | 限流 | 回放加 `--limit` 分批跑；或降并发（脚本本来就是串行） |
| 报 `HTTP 400` 且提示 model | 模型名不存在 | 以平台控制台当前列表为准，别照抄本文档 |
| 回答突然变短、没有 `边界` 段 | 被 `max_tokens` 截断 | 调到 1200 |
| 某些问题返回固定话术 | 被合规拦截 | `main.py` 的 `BLOCK_PATTERNS` 命中（治疗/手术/确诊类）。这是故意的，不是 bug |
| 每条都 2ms 返回 | 其实在降级 | 看 `degraded` 字段，别被速度骗了 |

## 成本

74 条回放，每条约 1.5k 输入 + 0.5k 输出 token。以 DeepSeek 当前定价，一轮回放是**几分钱**级别。可以放心反复跑，这也是为什么要建回放脚本而不是手点页面。

## 什么时候进第二阶段（视觉）

三条同时满足再动：

1. 文本回放四段式齐全率 ≥ 90%，编造 id = 0。
2. 你能说清楚「哪些问题检索没命中」，并且接受这个基线。
3. 前端 `read/clinic.html` 的上传框已经能拿到 data URL。

第 3 条是纯前端工作，和后端无关。第 1、2 条没过就加视觉，出问题时分不清是模型看错了图，还是检索本来就空——那时候排查成本会高很多。

加视觉只需要在 `.env` 里放开那三行，再把上传的图以 `"image": "data:image/jpeg;base64,..."` 塞进请求体，路由会自动切到视觉分支，不用改代码。

## 网页端：直连模型与自动回退

配好 key 后，读片工作台的「问答」页会自动切到直连模型，不需要手动改前端：

1. 页面启动时请求 `/api/health`，读 `llm_route.text`；
2. **无图 + 有文本模型** → `mode=llm`，省掉 agent 的十几秒；
3. **带图**或**没有文本模型** → 仍走 `mode=auto`（视觉定位 + agent 解释）。

失败时不会把本地模板直接甩给用户：

- 服务端 `mode=llm` 出错 → 返回 `served_by=fallback` + `degraded=true` + 原始错误；
- 前端发现「直连 + fallback + agent 可用」→ 自动用 `mode=agent` 重答一次（只重试一次，`forceAgent` 防循环），并 toast 提示原因。

所以 402 / 超时 / 网络故障时，用户看到的仍是 agent 的真实回答，只是多等十几秒，而不是一句模板话术。

不启动 HTTP 服务也能先验配置：

```bash
python3 kb/scripts/smoke_llm.py                 # 3 个固定问题，看耗时/四段式/引用
python3 kb/scripts/smoke_llm.py --q "肺水肿有哪些征象？"
python3 kb/scripts/smoke_llm.py --image kb/images/case-001.jpg   # 配了视觉 key 再跑
```

脚本直接 import `llm.py`，只验证「key 通不通、四段式齐不齐、引用是否真实」，不经过 agent。
