## 0. 一页结论

**v2.1 是「界面工程」，v3 改成「链路工程」。**

| 维度 | v2.1（现状） | v3（重规划） |
| --- | --- | --- |
| 交付主线 | 7 个入口 × 4 链条 × 3 角色 | **1 条可复现链路 + 4 个证据物** |
| 运行回执 | 前端 `traceHTML()` 拼文案 | 服务端 `trace_span` 落库，可回放 |
| Agent | 文档里的 §6.4 清单 | 真实调用，返回 `run_id` |
| 检索/判分 | 前端 + Python 两套口径 | 技能单一口径，前端只消费 |
| 记录 | localStorage，换机即失 | 会话表 + 聚合查询 |
| 入口 | 7 个 HTML（6 个是跳转包装） | 4 个真实入口，设备自适应 |
| 验收 | 76 项界面检查 | 界面检查 + 8 项链路检查 |
| 演示 | 7 分钟讲 7 个入口 | 7 分钟讲 1 条链路 + 80 秒讲证据 |

**一句话：把「我们有回执」改成「回执在这里，你可以自己 replay」。**

## 1. 为什么必须重规划：六个结构性问题

### P0-1 运行回执是假的（最高风险）

`traceHTML(title, steps)` 只是把调用方传入的字符串数组渲染成四段（[core.js](medtrain/app/core.js#L225)）。全项目搜索不到任何 span 采集、耗时、`run_id`。方案 §8.6 却把它列为「让评委看到这一步用了什么」的核心证据。

**后果**：评委只要说「换一个问题，你现场跑一次，把 trace 展开给我看」，就会暴露。这不是扣分，是可信度归零。

### P0-2 Agent 只存在于文档

方案 §6.4 的 10 行配置（4 技能 + 2 工作流 + 1 Agent）全部是「待发布」。当前可交付物里，DeepWorks 侧只有导入包（161 条记录）和文档。

**后果**：赛制硬约束「核心链路必须在 DeepWorks 内」目前无法被验证，只能靠讲解。

### P1-3 检索与判分有三套实现

| 位置 | 实现 |
| --- | --- |
| `kb/scripts/kbsearch.py` + `dual.py` | Python BM25 + 双线规则 |
| `medtrain/app/core.js` | 前端 JS 检索（`searchSigns`） |
| 方案 §6.4 技能 | 尚未存在 |

**后果**：改一处不同步另外两处，演示时数字对不上；「单引擎」的说法在代码层面不成立。

### P1-4 状态全在浏览器

`localStorage` 存 `learned / drills / reviewed / assignments`（方案 §5.3）。教师端「32 人演示班级」是造数。

**后果**：「真实任务、完整流程」（实用性 30 分）只能靠讲解，无法被评委验证。

### P2-5 七个入口是包装，不是能力

`build.py` 的 `VERSIONS` 生成 6 个页面，每个都是 `location.replace("app.html?role=...&device=...")`（[build.py](medtrain/build.py#L54)）。真正差异由同一个 `app.html` 渲染。

**后果**：技术上是 1 个引擎，叙事上却占了 7 个入口的篇幅。评委看穿后是减分项（「多版本 = 6 个跳转页」）。

### P2-6 验收只查界面，不查链路

方案 §11 的 76 项检查全部是「能打开 / 能到达 / 无溢出 / 无报错」。没有一条验证「回答是否真的来自知识库」「trace 是否真实」「判分是否与技能一致」。

**后果**：工程可信度建立在 UI 上，而评分要的是核心链路可复现。

## 2. 重规划的四个原则

| 原则 | 含义 | 反面 |
| --- | --- | --- |
| **链路先于界面** | 没有真实 `/api/ask` 之前，不再新增任何界面功能 | 继续做第 8 个入口 |
| **证据先于叙事** | 每个宣称的能力必须有可导出、可回放的产物 | 「我们有运行回执」但拿不出文件 |
| **单一口径** | 检索、双线、判分、审计只在技能层实现一次 | 前端和 Python 各写一套 |
| **降级要留痕** | 失败不是隐藏，而是显式状态 | 静默返回规则结果冒充 Agent |

## 3. 目标架构

### 3.1 三层与职责边界

```
┌────────────────────────────────────────────────────────────────┐
│ 表现层  4 个入口，设备自适应                                      │
│  /  演示台   /s 学生   /t 教师   /d 医生                          │
│  只做：渲染、交互、SSE 拼接、导出触发                             │
│  不做：检索、判分、trace 文案、prompt                             │
└──────────────────────────┬─────────────────────────────────────┘
                           │ HTTPS + SSE
┌──────────────────────────▼─────────────────────────────────────┐
│ 动态服务层 yingzhi-serve（薄，自建，约 900 行）                   │
│  · 会话与身份：session / role / device                          │
│  · 任务与记录：drill_attempt / review / assignment              │
│  · 链路留痕：trace_span（四段）+ citation + audit_event          │
│  · 缓存限流：kb_version / answer_cache / 并发闸门 8              │
│  · Agent Gateway：转发、落库、降级，**不编排**                    │
│  · 证据导出：trace.json / report.md / audit.csv                 │
│  ✗ 禁止出现：模型名、prompt、检索打分、判分规则                    │
└──────────────────────────┬─────────────────────────────────────┘
                           │ 只读知识 + 运行结果 + run_id
┌──────────────────────────▼─────────────────────────────────────┐
│ DeepWorks 核心（厚，比赛主体）                                    │
│  KB：signs / guidelines / cases / regions / claims（5 集合）     │
│  技能：retrieve_sign · dual_align · drill_score · citation_audit│
│  工作流：learning_chain · teaching_loop                         │
│  Agent：四段式回答 + run_id + 边界声明                           │
└────────────────────────────────────────────────────────────────┘
```

**边界判据（写进代码注释，答辩直接展示）**：动态服务层的任何文件里出现 `prompt`、`model`、`score(`、`bm25` 字样即为越界。

### 3.2 一次问答的数据流

```
用户输入
  → 前端 POST /api/ask（带 session_id / role / chain / filters / kb_version）
  → 服务层校验 → 写 request.json → 调用 DeepWorks
  → DeepWorks 返回 trace 四段 + 流式答案 + citations + run_id
  → 服务层逐事件转发（trace → delta → citation → done）
  → 落库 message / trace_span / citation
  → 前端渲染；done 后按钮「展开回执 / 复制 run_id」
```

### 3.3 数据模型（七表）

```sql
session(id, role, device, created_at, last_seen_at)
message(id, run_id, session_id, chain, query, answer, degraded, reason, kb_version, created_at)
trace_span(id, run_id, stage, skill, status, latency_ms, payload_json)
citation(run_id, cite_id, type, anchor_json, source_url, hash_ok)
drill_attempt(id, session_id, case_id, steps_json, score, wrong_json, run_id, created_at)
review_record(id, session_id, case_id, claim_id, verdict, created_at)
audit_event(id, kind, ref_id, detail_json, created_at)
```

SQLite 单文件；`payload_json` 保留原始返回，供回放与答辩。


评委可以现场给一个问题，跑完立刻 replay，证明「不是写死的」。

## 5. 工程结构

**落地位置**：新建顶层目录 `yingzhi/`（代码不放进 `outputs/`，避免污染产物面板）；`medtrain/app` 整体迁入 `yingzhi/app` 后原目录保留只读，`kb/` 与 `homepage/` 不动，通过构建脚本把数据产物同步到 `yingzhi/data/`。

```
yingzhi/
├── app/                      前端（沿用 medtrain/app，改造数据源）
│   ├── core.js               移除 searchSigns / 本地判分；新增 api.js 调用
│   ├── home.js  learn.js  transfer.js  drill.js
│   ├── apply-student.js  apply-teacher.js  apply-doctor.js
│   ├── sse.js                SSE 客户端：事件分发 + 重连 + 降级
│   └── styles.css
├── serve/                    动态服务层（新增）
│   ├── main.py               路由 + 静态托管（FastAPI 或 stdlib）
│   ├── gateway.py            Agent Gateway：转发 / 超时 / 降级
│   ├── store.py              SQLite 七表与迁移
│   ├── evidence.py           trace.json / report.md / audit.csv 导出
│   └── guard.py              kb_version 校验、并发闸门、越界词拦截
├── tools/
│   ├── replay.py             按 run_id 重放
│   ├── chain_check.py        8 项链路验收
│   └── ui_check.py           Playwright（沿用 76 项）
├── data/                     kb 构建产物（kb.js 仅作离线兜底）
└── deepworks/                KB 导入包 + 技能/工作流配置 + Agent 人设
```

**启动**：

```bash
python3 serve/main.py --port 8800        # 动态服务 + 静态
python3 tools/chain_check.py             # 链路验收
python3 tools/ui_check.py                # 界面验收
```

**离线包**：`serve/main.py --offline` 只用本地规则引擎，所有回答强制 `degraded=true`，界面顶部显示黄色条「本地演示态」。

## 6. 接口契约

### 6.1 `POST /api/ask`（SSE）

请求：

```json
{
  "session_id": "s_01H...",
  "role": "student",
  "device": "mobile",
  "chain": "kb_qa",
  "query": "磨玻璃影",
  "filters": { "body_part": "肺", "modality": "CT" },
  "context": { "case_id": "CASE-012", "step": "sign" },
  "client_kb_version": "2026-11-16"
}
```

事件序列（顺序固定）：

| 事件 | 载荷 | 前端行为 |
| --- | --- | --- |
| `trace` | `{stage, skill, status, ms}` × 4 | 立刻点亮四段，显示「正在检索」 |
| `delta` | `{text}` | 逐字追加 |
| `citation` | `{id, type, anchor, source_url, hash_ok}` | 出处卡片 + 图上锚点 |
| `done` | `{run_id, answer_id, degraded, reason, kb_version}` | 显示「展开回执 / 复制 run_id」 |
| `error` | `{code, fallback}` | 切本地规则 + 黄色提示条 |

四段固定为：`kb_retrieve` → `skill_invoke` → `workflow` → `agent_generate`。

### 6.2 其余接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/session` | 建会话，返回角色配置 |
| GET | `/api/records?session_id=` | 学习 / 演练 / 核验记录 |
| POST | `/api/drill/attempt` | 提交四步作答，判分来自 `drill_score` |
| POST | `/api/review` | 医生核验标记 |
| GET | `/api/class/{id}/summary` | 教师班级聚合 |
| GET | `/api/trace/{run_id}` | 回放四段链路 |
| GET | `/api/export/{session}.md` | 报告导出 |
| GET | `/api/audit.csv` | 审计导出 |

### 6.3 Agent 输出模板（不变）

```
结论：<只描述影像表现与库内对照>
依据：<词条/条款/病例 + 定位符/来源>
缺失：<未满足的适用条件；没有则写「无」>
边界：仅用于教学与研究，不构成诊断意见。
```

4. 诚实边界已做成机器可查的七条约束（检索命中数、引用 id 回查、降级不装、非真实数据带徽章），

## 9. 验收：从界面检查升级为链路检查

### 9.1 保留：界面验收（76 项）

`tools/ui_check.py` 不变，入口路径改为 `/s` `/t` `/d` 后重跑。

### 9.2 新增：链路验收（8 项）

| # | 检查 | 通过标准 |
| --- | --- | --- |
| 1 | SSE 事件顺序 | `trace×4 → delta+ → citation* → done`，无乱序 |
| 2 | trace 完整性 | 四段齐全，`latency_ms > 0`，`skill` 非空 |
| 3 | 可回放 | 同一 `request.json` 两次 replay，trace 结构一致（耗时允许差异） |
| 4 | 降级可见 | 断网时 `degraded=true`、`reason` 非空、界面有黄色条 |
| 5 | 判分一致 | 29 题前端得分与 `drill_score` 差值 = 0 |
| 6 | 引用拦截 | `audit.csv` 含 1 条 `hash_ok=false` |
| 7 | 会话隔离 | 两 session 记录互不可见；同 session 双端一致 |
| 8 | 越界拦截 | 输入「怎么治疗」→ 拒答 + 边界话术，不产生结论段 |

第 5、8 项是 v2.1 完全没有的，也是最容易被评委抽查的两项。

## 11. 七分钟演示脚本（v3 版）

| 时间 | 动作 | 讲解点 |
| --- | --- | --- |
| 0:00–0:40 | 演示台：三层架构一屏 | 「界面是薄的，核心在 DeepWorks」 |
| 0:40–2:00 | 学生 `/s`：问「磨玻璃影」→ 流式出字 → 展开回执 → 点 citation 跳图上分区 | 回答有出处、有耗时、有 run_id |
| 2:00–3:00 | 迁移：换模态/部位 → 三问 → 导出迁移卡 | 条件而不是结论 |
| 3:00–4:20 | 演练：四步 → 判分回执 → 错题入本 | 判分来自技能，不是前端 |
| 4:20–5:40 | 医生 `/d`：病例 → 分区 → 双引用 → hash 拦截 → 标记核验 | 每条结论能回到图上哪块、文献哪条 |

**与 v2.1 的关键差异**：把原来讲「第 7 个入口」的 80 秒，换成讲「证据可回放」。入口从 7 个降到 4 个，讲解深度反而上升。

## 14. 结论

1. **先修可信度，再修体验**。v3.0 只做一件事：让回答真的来自 DeepWorks，并且留下可回放的证据。
2. **入口从 7 降到 4**。省下的时间投到链路验收，收益更高。
3. **单一口径是硬要求**。前端不再有检索和判分，否则「单引擎」永远只是说法。
4. **降级必须可见**。`degraded=true` 比「假装一切正常」更可信。
5. **v3.0 不可砍，v3.2 可砍**。7 天内，链路是资格线，班级聚合是加分项。
