# 分区与结论反馈功能设计

> 版本：v1.0 ｜ 日期：2026-11-24 ｜ 关联：[用户反馈记录](用户反馈记录.md) FB-006 / FB-007、[AI 审核与人工终审](AI审核与人工终审_可行性与落地声明.md)

## 0. 一句话

**开发者不具备医学专业资质，影像分区没有人工标注**；分区与逐区文本来自「公开解剖分区规范 + 文献描述 + AI 辅助整理」。因此产品需要一个**能接住医师异议的入口**——不是加一句免责声明，而是让异议可提交、可追溯到具体病例与分区、可导出给复核人。

---

## 1. 为什么做这个功能

| 事实 | 产品后果 |
| --- | --- |
| 开发者无医学专业背景 | 不能声称「分区已由专业人员标注」 |
| 分区未人工标注 | 不能把分区框说成「人工标注解剖区」 |
| 分区来自文献 + AI 辅助整理 | 会有边界偏差、命名口径差异、结论与影像不完全对应的可能 |
| 尚未经影像科医师逐例复核 | 只能用于教学演示，不能用于临床 |

过去的问题是：**边界声明写在页面上，但用户发现问题后没有地方说**。专家复核因此没有输入，只能等有医师排期再从头看一遍。

这个功能把顺序倒过来：**先让异议进来，再让复核有靶子**。

---

## 2. 设计原则

1. **反馈不改结论**：提交反馈不会修改库内文本或分区，只新增一条「待专家复核」记录。
2. **可追溯**：每条反馈必须带病例 id、分区 id（整例反馈可为空）、问题类型、提交时间。
3. **不制造「已审核」的错觉**：所有反馈状态固定为「待专家复核」，页面不出现「已修正」「已通过」这类未经验证的措辞。
4. **不引入账号与服务端**：当前课堂数据都在 `localStorage`，反馈沿用同一策略；需要跨设备时再走同步服务。
5. **导出即可用**：导出的 CSV / JSON 能直接交给医学审核人逐条看，不需要再手工整理。

---

## 3. 反馈对象与类型

| 对象 | 入口 | 说明 |
| --- | --- | --- |
| 单个分区 | 右栏「分区所见」卡片 →「反馈这个分区」 | 针对分区框、分区名、该区结论 |
| 整例 | 右栏「出处」页 →「反馈本病例」 | 针对整例的分区体系、出处、许可信息 |

问题类型：

| 值 | 展示文案 | 典型场景 |
| --- | --- | --- |
| `bbox` | 分区框位置或范围不准 | 框没盖住肋膈角、跨区、明显偏移 |
| `zone_name` | 分区名称或解剖范围有误 | 把右肺中野标成下野、侧别写反 |
| `zone_text` | 分区所见与影像不符 | 影像上无该征象、描述超出分区范围 |
| `cite` | 出处或引用对不上 | 条款与结论不匹配、链接失效、段落错位 |
| `other` | 其他问题 | 表述、术语、教学适用性等 |

必填项只有「具体说明」（≥ 5 字）；身份（学生 / 教师 / 影像科医师 / 其他）与联系方式选填。**不强制实名**，避免因填写成本放弃反馈；但联系方式能让复核时回访。

---

## 4. 数据模型

存储键：`radiocheck.review.v1`（`localStorage`，最多保留最近 500 条）。

```json
{
  "at": "2026-11-24T07:52:11.302Z",
  "case_id": "CR-014",
  "case_title": "右下肺气腔影",
  "zone_id": "RLL",
  "zone_name": "右肺下野",
  "kind": "zone",
  "type": "bbox",
  "role": "影像科医师",
  "contact": "doctor@example.com",
  "note": "右侧肋膈角分区框略偏上，建议下移约一个肋间隙。",
  "status": "待专家复核",
  "page": "clinic",
  "quality": "可用"
}
```

字段约束：

- `kind`：`zone` | `case`
- `type`：上表五个枚举值
- `status`：当前固定 `待专家复核`；后续接入工作流后扩展为 `已复核` / `有异议` / `不采纳`
- `note`：去除首尾空白后 ≥ 5 字

---

## 5. 流程

```
用户在分区/整例上点「反馈」
        │
        ▼
  填写类型 + 说明（+ 身份 / 联系方式）
        │
        ▼
  写入 localStorage，状态 = 待专家复核
        │
        ├── 页面显示「已提交」，按钮出现数量徽标
        │
        ▼
  「我的反馈」→ 导出 CSV / JSON
        │
        ▼
  交给医学审核人逐条复核（线下 / 后续工作流）
        │
        ▼
  复核结论回填（下一阶段）：已复核 / 有异议 / 不采纳
        │
        ▼
  按结论更新库内文本或分区，并记录版本号
```

关键点：**提交与复核是两段**。当前版本只做前一段，且明确告诉用户「不会自动修改库内结论」。

## 6. 页面表现

| 位置 | 表现 |
| --- | --- |
| 分区卡片底部 | 「反馈这个分区」按钮；已有反馈时显示数量徽标 |
| 分区卡片「分区来源与审核状态」 | 写明分区范围来源、未人工标注、未专家复核 |
| 出处页「数据说明」 | 同上，并给「反馈本病例」按钮 |
| 反馈弹窗 | 目标信息 + 类型 + 说明 + 身份 + 联系方式 + 边界提示 |
| 提交后 | 切到「我的反馈」列表，状态显示「待专家复核」 |
| 列表底部 | 导出 JSON / 导出 CSV / 清空（二次确认） |
| 阅片记录导出 | 边界声明补一句「未人工标注、未专家复核，可通过页面反馈提交异议」 |

## 7. 导出格式

CSV 列（带 BOM，Excel 直接打开不乱码）：

```
提交时间,病例编号,病例标题,分区编号,分区名称,对象,问题类型,身份,说明,联系方式,状态
```

JSON 结构：

```json
{
  "exported_at": "2026-11-24T07:55:00.000Z",
  "status": "待专家复核",
  "source": "RadioCheck clinic · 分区与结论反馈",
  "count": 3,
  "items": [ ... ]
}
```

导出文件命名：`RadioCheck_反馈_YYYY-MM-DD.csv` / `.json`。

---

## 8. 明确不做什么

| 不做 | 原因 |
| --- | --- |
| 在线审核后台 | 没有真实医师排期，做出来是空转 |
| 反馈后自动改文本 | 会把未经复核的意见当成结论 |
| 反馈排行榜 / 公开墙 | 会诱导「凑反馈」，也会泄露病例讨论内容 |
| 强制实名 / 手机号 | 提高提交门槛，与「先收集异议」的目标冲突 |
| 上传服务器 | 当前无账号与服务端，上传会制造「已送达」的误解 |

## 9. 验收标准

- [x] 分区卡片与出处页均有反馈入口，按钮可打开弹窗
- [x] 说明少于 5 字时拦截并提示
- [x] 提交后写入 `radiocheck.review.v1`，状态为「待专家复核」
- [x] 「我的反馈」可查看全部记录，按时间倒序
- [x] CSV 导出含中文表头、说明字段完整、Excel 打开不乱码
- [x] JSON 导出含 `count` / `status` / `items`
- [x] 提交不改变库内分区与文本
- [x] 页面无 JS 报错，窄屏无横向溢出

## 10. 下一步（接 FB-006 核验工作流）

1. 反馈队列 → 审核表：按病例 / 分区聚合，同一位置的多条反馈合并展示。
2. 复核状态回填：`待专家复核 → 已复核 / 有异议 / 不采纳`，记录复核人、日期、版本号。
3. 页面核验徽标：按分区显示「未复核 / 已复核（复核人 + 日期）」，并给出核验覆盖率。
4. 版本联动：文本或分区改动后，原复核记录自动失效，回到「待复核」。
5. 触发条件：有具备资质的医学审核人并接受逐条签字流程。
