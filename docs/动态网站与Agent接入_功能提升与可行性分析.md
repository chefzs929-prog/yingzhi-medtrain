## 0. 一页结论

**值得做，但必须限定范围：动态网站只做「薄的有状态层」，Agent 只做「DeepWorks 内的厚编排」。**

| 判断 | 结论 | 依据 |
| --- | --- | --- |
| 要不要做动态网站 | 做，但只做 L2（会话 / 任务 / 审计 / 缓存 / 流式） | 现有服务已是只读 API，缺的正是状态与流式 |
| 要不要自建 Agent 编排 | **不要** | 赛制硬约束：核心链路必须在 DeepWorks 内 |
| 最大功能提升点 | 运行回执从「文案」变「真实 trace」 | 直接回应「壳工程」质疑，是评分证据 |
| 最大风险 | 自建后端把检索与编排做掉 → 赛制判违规 | 见 §5.2 |
| 时间可行性 | 中高，前提是 P0 只做 3 件事、≤2 人日 | 见 §7 |
| 建议动作 | 立刻做 P0（真实 Agent 通道 + trace 落库 + 降级开关），P1 视彩排余量决定 | 见 §7、§11 |

一句话：**动态化的价值不在「技术更先进」，而在把「可核对」这件事从界面话术变成可审计的数据。**

## 1. 先把「动态网站」定义清楚

「动态网站」在本项目里有四种完全不同的含义，混在一起讨论必然得出错误结论。按能力分级：

| 级别 | 定义 | 本项目现状 | 典型能力 |
| --- | --- | --- | --- |
| L0 静态站 | 纯 HTML/JS，数据打包进前端 | medtrain 前端（`data/kb.js` 1.4MB 全量加载） | 离线可跑，但无状态、无多人 |
| L1 只读 API | 服务端提供查询接口，无写操作 | `kb/scripts/serve_region.py`（4191）、`serve.py`（4180） | 按需取病例、定位、审计 |
| **L2 有状态服务** | 会话、写入、持久化、流式 | **尚未具备** | 学习记录、班级、任务、trace 落库 |
| L3 实时协作 | SSE / WebSocket 多端同步 | `duo-workspace` 已有 SSE 雏形（另一产品） | 投屏、多人演练、评委扫码参与 |
| L4 Agent 编排 | 服务端自行调模型、编排工具 | **不应具备**（赛制红线） | — |

**现状准确描述：L1.5。** 已有 HTTP API，但服务无状态、无持久化、无并发保护，所有「记录」都在浏览器 `localStorage`，所有「回答」都在浏览器里用规则拼装。

**目标应锁定 L2 + L4 交给 DeepWorks。** 不是 L4 自建。

## 2. 现状基线（事实与量化）

| 维度 | 现状 | 影响 |
| --- | --- | --- |
| 服务实现 | `ThreadingHTTPServer` 单进程，JSONL 全量读入内存 | 无鉴权、无写入、重启即丢状态 |
| 检索位置 | 浏览器内 BM25 / 规则（medtrain）；Python BM25（kb 服务） | 两套实现，口径可能漂移 |
| 首屏体积 | `kb.json` 1.8MB / `kb.js` 1.4MB 全量加载 | 移动端首屏慢，弱网演示有风险 |
| 判分 | 前端 `drill.js` 本地计分 | 无法防作弊、无法聚合班级 |
| 双线判断 | 前端规则输出 aligned/partial/insufficient/divergent | 与技能层契约未对齐 |
| 运行回执 | `traceHTML()` 前端拼接的四段文案（`medtrain/app/learn.js:145`） | **看起来像链路，实际没有链路** |
| 记录 | `localStorage`（学习、迁移卡、核验） | 换设备即失，教师看不到学生数据 |
| Agent | 无真实调用；`docs/多版本软件方案.md` §6.4 为待发布清单 | 评委追问「Agent 在哪」时只能指文档 |

数据规模（可作为 Agent 召回压力基线）：60 征象 / 47 条款 / 120 病例 / 615 分区 / 599 双引用结论 / 29 道题 / 导入包 161 条记录。

## 3. 功能提升评估

按「痛点 → 动态化贡献 → Agent 贡献 → 提升幅度」拆开，避免把两件事的收益混算。

### 3.1 逐项评估

| # | 能力 | 现状痛点 | 动态化（L2）贡献 | Agent 接入贡献 | 提升 | 必要性 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 真实回答链路 | 回执是前端文案，一问就露 | trace 四段落库、可回放 | 真实技能调用产生 span | ★★★★★ | 必须 |
| 2 | 首字延迟 | 全量 1.4MB JS + 本地检索后才渲染 | SSE 流式，1–2s 出字 | 流式生成 | ★★★★☆ | 必须 |
| 3 | 跨设备记录 | localStorage，换机即失 | 会话表 + 用户标识 | — | ★★★★☆ | 高 |
| 4 | 教师班级数据 | 班级数据是本地造数 | 服务端聚合演练/作业 | 错题归因 | ★★★★☆ | 高 |
| 5 | 引用审计 | 前端校验 hash，无留痕 | 审计事件表 + 导出 | 审计技能统一口径 | ★★★☆☆ | 高 |
| 6 | 多人现场参与 | 单机 localStorage，无法并发 | 会话隔离 + 限流 | — | ★★★☆☆ | 中 |
| 7 | 知识热更新 | 改数据要重建前端包 | 服务端版本号 + 缓存失效 | KB 版本随 Agent 走 | ★★★☆☆ | 中 |
| 8 | 回答一致性 | 前端规则与 Python 检索两套口径 | 统一到服务端单一入口 | 技能为唯一口径 | ★★★★☆ | 高 |
| 9 | 内容运营 | 无埋点，不知道学生卡在哪 | 事件表 + 漏斗 | — | ★★☆☆☆ | 低 |

### 3.2 需要警惕的「伪提升」

这四条是常见误判，必须在方案里写死，否则会浪费 2–3 天：

| 伪提升 | 为什么不是提升 |
| --- | --- |
| 把 BM25 从浏览器搬到服务端 | 算法没变，召回质量不变；收益只是体积与可维护性 |
| 引入数据库 | 数据规模 1.8MB，SQLite 足够；换 PG 不带来任何演示差异 |
| 自建 Agent 编排（自己调 LLM） | 违反「核心链路在 DeepWorks」硬约束，风险远大于收益 |
| 做微服务 / 容器化 | 7 天内无收益，只增加现场故障面 |

### 3.3 提升的本质

把三件事从「界面声明」变成「系统事实」：

1. **回答有出处** → trace 里有 span、有 KB 版本、有 citation id。
2. **记录有归属** → 有 session、有 role、有 device，可回放。
3. **降级有痕迹** → `degraded: true` + 原因码，而不是静默返回规则结果。

这三点正好对应评分维度里的「可行性（可复现）」「真实任务（完整流程）」「最终成品（可演示）」。

## 4. 目标架构

### 4.1 分层与职责边界

```
┌──────────────────────────────────────────────────────────────┐
│ 表现层  7 个入口 / 3 角色 / 双设备                              │
│  只做渲染、交互、流式拼接；不做检索、不做判分、不做 trace 文案    │
└───────────────────────────┬──────────────────────────────────┘
                            │ HTTPS + SSE
┌───────────────────────────▼──────────────────────────────────┐
│ 动态服务层（薄，自建）                                          │
│  · 会话与身份：session / role / device                         │
│  · 任务与记录：drill_attempt / review / assignment             │
│  · 链路留痕：trace_span（四段）+ audit_event                    │
│  · 缓存与限流：KB 版本号、答案缓存、并发闸门                     │
│  · Agent Gateway：只转发、只落库、只降级，**不编排**             │
└───────────────────────────┬──────────────────────────────────┘
                            │ 只读调用 + 运行结果
┌───────────────────────────▼──────────────────────────────────┐
│ DeepWorks 核心（厚，比赛主体）                                  │
│  KB：征象 / 条款 / 病例 / 分区 / 双引用                          │
│  技能：retrieve_sign · dual_align · drill_score · citation_audit│
│  工作流：learning_chain · teaching_loop                         │
│  Agent：汇总为「结论 / 依据 / 缺失 / 边界」四段式回答             │
└──────────────────────────────────────────────────────────────┘
```

**边界判据（写进代码注释与答辩口径）**：动态服务层里不允许出现 prompt、模型名、检索打分函数、判分规则。出现即违规。

### 4.2 关键接口

**主通道：`POST /api/ask`（SSE 流式）**

```json
{
  "session_id": "s_01H...",
  "role": "student",
  "device": "mobile",
  "chain": "kb_qa",
  "query": "磨玻璃影",
  "filters": { "body_part": "肺", "modality": "CT" },
  "context": { "case_id": "CASE-012", "step": "sign" },
  "client_kb_version": "2026-11-15"
}
```

事件序列（顺序固定，前端按序渲染）：

| 事件 | 载荷 | 用途 |
| --- | --- | --- |
| `trace` | `{stage, skill, status, ms}` × 4 | 立刻点亮四段回执，先给「正在做什么」 |
| `delta` | `{text}` | 逐字输出，首字目标 < 2.5s |
| `citation` | `{id, type, anchor, source_url, hash_ok}` | 渲染出处卡片与图上锚点 |
| `done` | `{answer_id, degraded, reason, kb_version}` | 落库并允许「回放本次回答」 |
| `error` | `{code, fallback}` | 前端切本地规则并显示「本地演示态」 |

**其余接口**

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/session` | 建会话，返回 session_id 与角色配置 |
| GET | `/api/records?session_id=` | 学习 / 演练 / 核验记录 |
| POST | `/api/drill/attempt` | 四步作答与判分结果（判分来自技能） |
| POST | `/api/review` | 医生核验标记 |
| GET | `/api/class/{id}/summary` | 教师班级聚合 |
| GET | `/api/audit` | 审计事件（含 1 条 hash 拦截） |
| GET | `/api/trace/{answer_id}` | 回放四段链路 |

### 4.3 最小数据模型

```sql
session(id, role, device, created_at, last_seen_at)
message(id, session_id, chain, query, answer, degraded, reason, kb_version, created_at)
trace_span(id, message_id, stage, skill, status, latency_ms, payload_json)
citation(message_id, cite_id, type, anchor_json, source_url, hash_ok)
drill_attempt(id, session_id, case_id, steps_json, score, wrong_json, created_at)
review_record(id, session_id, case_id, claim_id, verdict, created_at)
audit_event(id, kind, ref_id, detail_json, created_at)
```

七张表，SQLite 单文件，够用；`payload_json` 保留原始返回，便于复现与答辩。

### 4.4 Agent 契约（与 §6.4 落地清单对齐）

请求侧固定四段输入：`query + filters + role + chain`。
响应侧固定四段输出：

```
结论：<只描述影像表现与库内对照>
依据：<词条/条款/病例 + 定位符/来源>
缺失：<未满足的适用条件；没有则写「无」>
边界：仅用于教学与研究，不构成诊断意见。
```

服务端只做三件事：校验、转发、落库。**不改写、不补全、不推断。**

## 5. 可行性评估

### 5.1 技术可行性：高

| 项 | 评估 | 依据 |
| --- | --- | --- |
| 服务框架 | 高 | 现有 `ThreadingHTTPServer` 可平滑换 FastAPI/Starlette；也可先用标准库加 SSE（`duo-workspace/server.js` 已有 SSE 参考实现） |
| 持久化 | 高 | SQLite 单文件，1.8MB 数据量无压力 |
| 流式 | 高 | SSE 比 WebSocket 简单，穿透代理友好，半天可通 |
| 改造面 | 中 | 前端需把 `learn.js` / `drill.js` 的本地规则改为调用；约 300–400 行改动 |
| 联调成本 | 中 | 依赖 DeepWorks 侧技能/工作流就绪（§6.4 清单尚未发布） |

### 5.2 赛制与合规可行性：**中高风险（关键约束）**

这是本方案唯一可能「做了反而扣分」的地方，必须显式设计。

| 风险 | 后果 | 规避 |
| --- | --- | --- |
| 动态层自己实现检索/判分 | 被判「自建后端 + 壳页面」，资格风险 | 代码层禁止出现打分函数与 prompt；回执显示 DeepWorks 运行 ID |
| Agent 由服务端直调模型 | 核心链路不在 DeepWorks，直接违背硬约束 | Gateway 只转发；模型调用凭证不下发到服务端 |
| 记录含患者信息 | 合规红线 | 仅存 session 与病例公开 ID，不存任何个人健康信息 |
| 回答被当作诊断 | 赛道 B 合规风险 | 四段式固定「边界」段；服务端做越界词拦截 |

**结论**：动态化的收益（状态、流式、审计）与合规风险可以共存，前提是把「智能」全部留在 DeepWorks，服务端只做「管道 + 账本」。

### 5.3 时间可行性：中（7 天窗口）

| 阶段 | 内容 | 人日 | 可独立演示 |
| --- | --- | --- | --- |
| P0 | `/api/ask` 接 DeepWorks + SSE + trace 落库 + 降级开关 | 1.5–2 | 是 |
| P1 | SQLite 会话/记录/班级聚合 | 2 | 是 |
| P2 | 扫码参与 + 投屏 + 审计导出 | 1.5 | 是 |
| P3 | 20 并发压测 + 断网演练 + 离线包 | 1 | 是 |

P0 若在 11-18 前跑通，P1 可与技能发布并行；否则砍掉 P2，保 P0+P3。

### 5.4 演示稳定性：中

| 风险 | 应对 |
| --- | --- |
| DeepWorks 现场网络异常 | 本地规则引擎兜底，界面明示「本地演示态」，trace 标 `degraded` |
| 首字慢 | trace 事件先行，先出「正在检索」，避免白屏 |
| 并发卡顿 | 单进程 + 并发闸门（上限 8），超限排队并提示 |
| 数据版本不一致 | 请求带 `client_kb_version`，不匹配则强制刷新缓存 |

### 5.5 综合评分

| 维度 | 分数（5 分制） | 说明 |
| --- | --- | --- |
| 功能价值 | 4.5 | 直击「壳工程」质疑，提升可核对性 |
| 技术可行 | 4.5 | 改造面可控，无新依赖 |
| 赛制合规 | 3.0 | 边界清晰才安全，需要纪律 |
| 时间可行 | 3.5 | 只够 P0+P1，P2 需砍 |
| 演示收益 | 4.0 | 流式与真实 trace 观感提升明显 |
| **加权结论** | **3.9 / 5** | **做 P0，P1 视进度，P2 只做彩排级** |

## 6. 不做什么（反模式清单）

写进方案，防止执行中跑偏：

1. 不做用户注册/登录体系 —— 用匿名 session + 邀请码即可。
2. 不做微服务、不做容器编排 —— 单进程 + SQLite。
3. 不做向量库 —— 60 条征象用 BM25 + 同义词已够，向量化只增延迟。
4. 不做自建 LLM 调用 —— Agent 只在 DeepWorks。
5. 不做图片上传与分析 —— 合规红线，且无演示价值。
6. 不重写前端框架 —— 保持现有单引擎 + 参数化角色，只换数据源。
7. 不为「动态」而动态 —— 每个接口必须对应 §3.1 表里的一行。

## 9. 验收指标（可量化）

| 指标 | 目标 | 测法 |
| --- | --- | --- |
| 首字延迟 P95 | < 2.5s | SSE 首个 `delta` 时间戳 |
| 回答成功率 | ≥ 99%（含降级） | 100 次请求统计 |
| trace 完整率 | 100% | 四段 span 齐全的 message 占比 |
| 首屏 JS 体积 | 下降 ≥ 40%（1.4MB → < 800KB） | 构建产物对比 |
| 记录一致性 | 100% | 双端比对 |
| 降级可见率 | 100% | `degraded=true` 时界面必现提示 |
| 审计留痕 | ≥ 1 条拦截可导出 | `/api/audit` |

---

## 10. 结论与建议

1. **做，但只做 P0 + P1。** P0 解决「回答是真是假」，P1 解决「记录是不是数据」。这两件是评分能看见的。
2. **P2 降级为彩排选项。** 扫码参与观感好，但 7 天内优先级低于稳定性。
3. **守住一条线**：动态层不产生任何「智能」。所有 prompt、检索、判分、审计口径留在 DeepWorks，服务端只做会话、转发、落库、降级。
4. **最大收益不是技术，是答辩素材**：`/api/trace/{answer_id}` 可以当场回放一次回答的完整链路，这是回应「壳工程」最硬的证据。
5. **如果只剩一天**：只做 P0 的 `trace` 落库 + `degraded` 标记，也比现在的前端文案强。
