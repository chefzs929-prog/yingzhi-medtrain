> 版本：v1.0 ｜ 日期：2026-11-18 ｜ 承接 [影像精确分区与报告指南解读_评估](影像精确分区与报告指南解读_评估.md)

> 一句话结论：**现在能扩"例数"，不能扩"知识密度"；瓶颈不是存储，是内容生产模型与审核人力。**

## 0. 结论摘要

| 问题 | 结论 |
| --- | --- |
| 当前最大痛点 | **容量在涨，知识没涨**：582 条分区结论只有 **76 种不同文本**，由脚本按「分区 × 征象」模板拼接 |
| 第二痛点 | **文献侧空心**：577/582 的"文献"是征象释义；60 个征象只用了 13 个，47 条指南只用了 4 条 |
| 第三痛点 | **审核缺位**：`annotator = "template"`，没有医学签字；扩容量会把"未审核"同比放大 |
| 技术扩容 | **可行**：脚本化，约 1–2 人日可把例数翻 8 倍 |
| 知识扩容 | **不可自动化**：每例 15–50 分钟人工，1000 例约 1.5–5 个月/人 |
| 工程承载 | 约 **400 例**是现有"全量打包"的舒适上限；**1200 例**必须 API 化；**5000 例**必须 CDN + 审核团队 |
| 最终天花板 | 不是存储，是**医学审核人力**：1 名审核按 10 分钟/例、半工时，约 3000–4000 例/年 |

## 1. 容量现状：三个数字说明一切

### 1.1 结论文本：582 条 → 76 种

```
claims.jsonl        582 条
唯一文本            76 条   （13.1%）
前缀种类            69 种
最大同文簇          27 条（右肺上野 / 右肺中野 / 右肺下野 / 左肺上野 … 各 27 条）
中位长度            63 字，其中约 35 字是固定套话
```

模板出处是 [build_corpus_120.py](kb/scripts/build_corpus_120.py#L414)：

```python
text = (f"{r['name']}区域解剖范围为{r['note']} "
        f"库内关联征象包括{names}；本条目只作分区与征象对照，不构成诊断。")
```

变量只有三个：分区名、分区 note、征象名列表。**换一张图、换一个病例，文本不变。**

### 1.2 征象覆盖：60 个 → 用了 13 个

| 指标 | 实测 | 含义 |
| --- | --- | --- |
| 征象词条 | 60 | 库里的"知识单元" |
| 被 claim 引用过 | **13（21.7%）** | 47 个征象从未进入任何结论 |
| 每条 claim 引用 | 1–2 个 | 不是"多征象鉴别"，是"一区一征象" |

### 1.3 指南覆盖：47 条 → 用了 4 条

| 指标 | 实测 | 含义 |
| --- | --- | --- |
| 指南条款 | 47（10 个标准） | Lung-RADS、TI-RADS、BI-RADS、Fleischner 等 |
| 被 claim 引用 | **4（8.5%）** | 43 条从未参与回答 |
| 有 `guideline_ids` 的 claim | **4 / 582 = 0.7%** | 指南基本没进问答 |
| 指南段落长度 | 中位 29 字 | 是一句摘要，不是原文段落 |

### 1.4 结构比例：一区一条，机械对应

| 指标 | 实测 |
| --- | --- |
| 分区总数 | 596 |
| 结论总数 | 582 |
| 结论 / 分区 | **0.98** |
| 每例分区 | 3–8 个（中位 5） |
| 每例结论 | **117/120 例与分区数 1:1**；另 3 例（CASE-001/006/011）是人工标注 |

**这四组数字合起来只有一个含义**：库的"容量"是**分区数量的线性函数**，不是"知识量"的函数。扩 10 倍病例，唯一文本大概率仍停在 70–100 条。

## 2. 最大痛点排序

### P0 · 内容同质化：扩容量 ≠ 扩知识

- 证据：582 → 76 唯一文本；117/120 例是 1:1 模板实例化
- 后果：病例数从 120 涨到 1200，用户看到的解释几乎一样；"库变大了"在演示上是真的，在临床思维训练上是假的
- 根因：把"知识生产"降级成了"字符串拼接"
- 影响扩容：**这是最致命的**——它让"扩容"变成一个可以刷的数字，而不是一个要投入的工程

### P1 · 文献侧空心：引用链没有真实文献支撑

- 证据：577/582 锚点是 `doc_kind=sign`（征象释义）；指南覆盖 0.7%；582 条全是 8 位截断 hash、无页/段/偏移
- 后果：扩容量时，每条新 claim 仍然只能挂"词条释义"，"引用文献段落"永远名不副实
- 影响扩容：文献库是**一次性建设、边际成本低**的部分，现在没建，等于每扩一例都在重复欠账

### P2 · 审核缺位：`annotator=template`，没有医学签字

- 证据：`regions.jsonl` 中 `annotator=template` **575 条**、`human` **21 条**；`claims.jsonl` 甚至没有 `annotator` 字段（582 条全为 `None`）
- 后果：模板生成的解剖范围、征象关联**没有经过医学审核**；扩容量时错误同比放大
- 影响扩容：**这是扩容的真正天花板**——脚本可以一秒生成 1000 条，但没有 1000 条对应的审核工时

### P3 · 元数据缺口：60% 分区没有侧别

- 证据：`patient_side` 分布 `unknown 359 / midline 63 / right 87 / left 87`；可校验率 29.2%
- 后果：侧别校验、报告-影像一致性校验都跑不起来；扩容量会把"无法校验"的比例原样放大
- 影响扩容：每新增一例，如果仍用模板，`unknown` 会继续占 60%

### P4 · 前端全量打包：1.58 MB / 120 例

- 证据：`kb.json` 1.58 MB，其中 `regionsByCase` 0.396 MB + `claimsByCase` 0.686 MB = **68%**
- 推算：每例约 13 KB → 400 例 5.2 MB、1200 例 15.6 MB、5000 例 65 MB
- 后果：首屏 JSON 解析在移动端会明显卡顿；这是**第一个会"崩"的工程点**
- 影响扩容：约 400 例后必须分片/懒加载，1200 例后必须 API 化

### P5 · 版权与去标识：逐例核验，风险线性增长

- 证据：`sources` 11 条、`fetch_commons.py` 等抓取脚本；图片 158 张 / 34 MB
- 风险：公开许可（CC-BY / 公有领域）需逐例核对；DICOM 头、图像上的姓名/日期需去标识
- 影响扩容：每扩一例就多一份许可与去标识责任，**不能靠脚本"批量免责"**

## 3. 三条扩容路径与成本模型

### 路径 A · 继续模板生成（现状）

| 项 | 数值 |
| --- | --- |
| 每例耗时 | 2–5 分钟（套模板 + 跑脚本） |
| 1000 例 | **1–2 人日** |
| 唯一文本 | 仍约 76–100 条 |
| 征象覆盖 | 不增（仍 13/60） |
| 指南覆盖 | 不增（仍 4/47） |
| 审核 | 无 |
| 结论 | **能刷例数，不能刷知识**；只适合做压力测试/演示规模 |

### 路径 B · 全人工撰写

| 项 | 数值 |
| --- | --- |
| 每例耗时 | 影像筛选 10 + 分区核对 5 + 结论撰写 15–20 + 指南锚定 10 + 审核 10 = **50–55 分钟** |
| 1000 例 | **830–920 人时 ≈ 5 个月/人** |
| 唯一文本 | ≈ 100% |
| 征象覆盖 | 可到 80%+ |
| 指南覆盖 | 可到 50%+ |
| 结论 | 质量最高，但黑客松/小团队不可承受 |

### 路径 C · 混合（推荐）

分工：**模板出骨架，人做判读**。

| 环节 | 谁做 | 耗时 |
| --- | --- | --- |
| 找图 + 去标识 + 许可登记 | 脚本 + 人核 | 3 分钟 |
| 分区（3 标志点 + 模板） | 脚本 + 人核 | 2 分钟 |
| 候选征象（模板召回 Top-3） | 脚本 | 0 |
| 选定征象 + 写 1–2 句结论 | 人 | 6–8 分钟 |
| 指南锚定（段落库检索 + 人工确认） | 脚本 + 人 | 3 分钟 |
| 医学审核签字 | 审核人 | 5–8 分钟 |
| **合计** | | **19–24 分钟/例** |

| 项 | 数值 |
| --- | --- |
| 1000 例 | **320–400 人时 ≈ 2–2.5 个月/人**（双人并行约 1–1.5 个月） |
| 唯一文本 | 可达 70–85%（仍保留少量模板句） |
| 征象覆盖 | 可达 70–80% |
| 指南覆盖 | 可达 40–60% |
| 结论 | **质量与成本的最佳平衡点** |

### 三路径对比

| 维度 | A 模板 | B 全人工 | C 混合 |
| --- | --- | --- | --- |
| 1000 例成本 | 1–2 人日 | 5 个月/人 | 2–2.5 个月/人 |
| 唯一文本率 | 13% | ~100% | 70–85% |
| 征象覆盖 | 22% | 80%+ | 70–80% |
| 指南覆盖 | 8.5% | 50%+ | 40–60% |
| 可审核 | 否 | 是 | 是 |
| 适用场景 | 压测/演示 | 精品库 | **生产库** |

**判断**：如果目标只是"把 120 例变成 1200 例"，路径 A 一天就能做完，但它在答辩时经不起一句追问——"这两条结论为什么一模一样？"如果目标是"可持续扩大的知识库"，只有路径 C 成立。

## 4. 工程承载阈值

### 4.1 数据体积

| 例数 | kb.json | 图片（140 KB/张） | 结论 |
| --- | --- | --- | --- |
| 120（现状） | 1.58 MB | 34 MB | 全量打包可接受 |
| 400 | ~5.2 MB | ~110 MB | 首屏开始吃力，建议分片 |
| 1200 | ~15.6 MB | ~340 MB | **必须 API 化 + 按需加载** |
| 5000 | ~65 MB | ~1.4 GB | **必须 CDN + 对象存储 + 分页** |
| 20000 | ~260 MB | ~5.6 GB | 需要独立检索服务（向量/倒排） |

### 4.2 检索

| 项 | 现状 | 扩容影响 |
| --- | --- | --- |
| 索引 | `kb/index/index.json` 269 KB / 149 文档 | 1.8 KB/文档；10 万文档约 180 MB |
| 算法 | 纯标准库 BM25 + 同义词 + 元数据过滤 | 线性打分；10 万文档单查询约数百 ms，可接受 |
| 瓶颈 | 全量加载进内存 | 100 万文档需倒排分片/向量库 |

### 4.3 前端

| 项 | 现状 | 扩容影响 |
| --- | --- | --- |
| 数据注入 | 构建时读 `kb.json` 打进页面 | 例数线性增长 |
| 首屏 | 1.58 MB | 400 例后建议按部位/系统分片 |
| 图片 | 静态目录 | 5000 例后必须 CDN |

**工程结论**：技术侧没有"做不到"的坎，只有"什么时候必须改架构"的阈值。**400 例是第一道坎，1200 例是第二道。**

## 5. 影响持续扩容的六个因素（可行性判断）

| 因素 | 现状 | 扩容 10 倍会怎样 | 可行性 |
| --- | --- | --- | --- |
| 影像供给 | 158 张公开影像 | 需 1500+ 张，许可核验线性增长 | **可行但慢**，需建立许可台账 |
| 分区标注 | 模板 + 3 标志点（L1） | 每例 2 分钟，可脚本化 | **可行**，L1 是扩容的关键使能项 |
| 结论撰写 | 模板拼接 | 不投入人工则知识密度不增 | **不可自动化**，必须人工 |
| 文献锚定 | 4/47 指南 | 段落库一次性建设后可复用 | **可行**，边际成本低 |
| 医学审核 | 基本缺失 | 线性人力，无法脚本化 | **最终瓶颈** |
| 版权/去标识 | 逐例人工 | 风险线性增长 | **必须制度化**，不能靠脚本 |

## 6. 扩到 1000 例的 90 天方案

### 第 1–2 周：骨架与门禁

- 建 6 套体位多边形模板（胸 PA/侧、膝正侧、手正、颈侧）
- 段落库 v1：47 指南 + 60 征象，`page/para/span/64 位 hash/快照`
- 侧别元数据补齐规则 + `unknown` 清理
- 建立"扩容质量门"脚本（见第 7 节）

### 第 3–6 周：批量生产（混合路径）

- 每周目标 120–150 例（2 名标注 + 1 名审核）
- 每例：模板骨架 → 人工选征象/写结论 → 指南锚定 → 审核签字
- 每周抽检 10%，唯一文本率低于 60% 则停工复盘

### 第 7–10 周：工程改造

- `kb.json` 拆分：`cases.index.json` + 按例分片 + 按需加载
- 图片迁 CDN / 对象存储
- 检索加倒排分片，保留 BM25 兜底

### 第 11–13 周：验收与冻结

- 跑第 7 节全部指标
- 未过门的病例不进正式库，进 `staging`
- 冻结 v2.0，出扩容白皮书

## 7. 扩容质量门（比"例数"更重要的指标）

| 指标 | 现状 | 目标 | 为什么重要 |
| --- | --- | --- | --- |
| 唯一结论文本率 | **13.1%** | ≥ 70% | 防"复制粘贴式扩容" |
| 征象覆盖率 | **21.7%** | ≥ 80% | 防"60 个词条只用 13 个" |
| 指南覆盖率 | **8.5%** | ≥ 50% | 防"文献侧空心" |
| 分区侧别完整率 | **29.2%** | ≥ 95% | 让侧别校验跑得起来 |
| 医学审核签字率 | **≈0**（claims 无 annotator 字段） | 100% | 扩容的合法性基础 |
| 双引用完整率 | 580/582 | 100% | 已有基础，保持 |
| 每例平均审核时长 | 0 | ≥ 8 分钟 | 防"批量盖章" |

**关键**：扩容验收不看"病例数"，看这 8 个比值。**例数可以一天翻 8 倍，比值不能。**

## 8. 结论：能扩到多少，什么时候必须停

### 三句话

1. **技术上能扩**：脚本化到 1000 例是 1–2 人日的事，工程阈值在 400 / 1200 例。
2. **知识上不能自动扩**：唯一文本率 13%、征象覆盖 22%、指南覆盖 8.5%，这三个数字不解决，扩容量只是把同一条结论复制更多遍。
3. **真正的天花板是审核**：1 名医学审核按 10 分钟/例、半工时，约 3000–4000 例/年。这是"可持续"的物理上限。

### 扩容决策树

```
目标只是演示规模？
  └─ 是 → 路径 A，1 天扩到 1000 例，但答辩时不要声称"知识库扩大"
  └─ 否 → 目标是不是"可持续的知识库"？
        └─ 是 → 路径 C + 质量门 + 审核签字
              ├─ 400 例内：现有架构直接撑
              ├─ 400–1200 例：分片 + 懒加载
              └─ 1200 例以上：API 化 + CDN + 审核团队
```

### 什么时候必须停

| 信号 | 含义 | 动作 |
| --- | --- | --- |
| 唯一文本率 < 40% | 在刷量，不是在建库 | 停止扩例，转内容生产 |
| 审核签字率 < 80% | 库不可信 | 停止上线，补审核 |
| 侧别完整率 < 60% | 校验链失效 | 先修元数据 |
| kb.json > 5 MB | 首屏要崩 | 先分片再扩 |
| 许可台账缺项 | 版权风险 | 先补台账 |

## 9. 一句话总结

**当前最大的痛点不是"库太小"，是"库在虚胖"：582 条结论只有 76 种说法，60 个征象只用了 13 个，47 条指南只用了 4 条。**

扩容的可行性不在存储、不在脚本，而在**愿不愿意把"字符串拼接"换成"人工判读 + 医学签字"**。前者能把例数一天翻 8 倍，后者能把知识密度翻 5 倍——**只有后者叫"持续扩大"，前者叫"重复导入"。**
