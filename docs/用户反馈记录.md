## 二、已修复条目

### FB-002 Agent 无反应，只能在本地使用（第 1 个修复）

- **反馈日期**：2026-11-23
- **反馈来源**：真实用户
- **用户原话（整理）**：Agent 无反应，只能本地使用。
- **根因定位**：
  1. `kb/app/agent-lite.js` 的地址解析只有两种结果：纯静态托管时硬编码 `http://127.0.0.1:8800`，其余情况走同源 `/api/*`。线上页面既没有同源后端，也不能从 HTTPS 直连 HTTP 本地服务，因此必然失败。
  2. 失败后只提示「线上页面不能直接访问本地服务」，没有任何改地址的入口，用户无法自救，表现就是「点了没反应 / 只能本地用」。
  3. 关联提交 `7b781a7` 只补了降级提示，没解决「线上指向哪里」的问题。
- **修复内容**：
  - 地址优先级改为：`window.RC_AGENT_BASE` → URL `?agent=` / `?api=` → 用户保存的地址（localStorage `radiocheck.agent.base`，兼容旧键 `yzApiBase`）→ 同源 / 本地默认。
  - 新增「连接设置」对话框：可填写 HTTPS Agent 地址、测试 `/api/health`、一键切到本地 8800、清除配置；保存后即时生效，无需刷新。
  - 探测失败按原因分类：未配置 / HTTPS 混合内容 / 超时 / 网络不可达，各自给可执行提示。
  - `ask()` 在未配置或混合内容时直接给出明确错误码，不再落到模糊的「无法连接本地 Agent」。
  - 问答失败面板与阅片工作台的错误卡片都带「连接设置」按钮；按钮样式由脚本自注入，不依赖页面是否引入 `agent.css`。
- **改动文件**：`kb/app/agent-lite.js`、`kb/app/clinic.js`
- **验证**：
  - 指向不可达地址 → 出现「智能解释暂时不可用 + 连接设置」，点击可打开对话框；
  - 点「用本地 8800」→ 显示「已连接（Agent 就绪）」，地址写入 localStorage；
  - 正常提问（本地 8800）→ 约 30 秒返回并正常渲染，无 page error。
- **状态**：已修复

### FB-004 胸片样本少，不够用

- **反馈日期**：2026-11-23
- **反馈来源**：真实用户
- **用户原话（整理）**：胸片样本少，不够用。
- **现状**：21 例 CR 胸部进入队列（23 例中 2 例因多图拼接 / 双幅对照移出），10 例大纲病例题，8 组易混对比。
- **为什么现在不做**：
  1. 扩容不是复制图片，而是「授权影像 + 逐区标注 + 双引用 + 易错点」的内容生产，单例成本高；
  2. 现有 21 例已做到逐区可回查，盲目加量会稀释标注质量；
  3. 需要医学审核人力，当前没有稳定的审核排期。
- **未来方向**：
  - 先做「考点覆盖矩阵」，按大纲高频考点找缺口，再定向补例（优先肺炎 / 结核 / 肺癌 / 气胸 / 积液 / 骨折 / 心型）；
  - 建立影像授权台账（CC0 / CC BY / CC BY-SA / 公有领域）与逐例署名；
  - 目标区间：先到 50 例可逐区回查，再考虑 100 例。
- **触发条件**：有稳定的公开授权影像来源 + 医学审核人力。
- **结论**：不修复

### FB-005 建议添加与教师私信的窗口

- **反馈日期**：2026-11-23
- **反馈来源**：真实用户
- **用户原话（整理）**：建议添加与教师私信的窗口。
- **现状**：课堂只有「班级 + 作业 + 小组论坛（异步帖子）」，没有一对一私信。
- **为什么现在不做**：
  1. 实时私信需要账号体系、身份认证与服务端消息存储；当前课堂数据全部存在浏览器 localStorage，没有真实身份，做出来只是「同一台电脑上的假对话」；
  2. 师生私信涉及未成年人场景与消息留存合规，需要明确边界与审计策略，不能先上线再补；
  3. 单机演示无法保证消息真正送达，反而会制造「以为发出去了」的误解。
- **未来方向**：
  - 第一步：先做异步「提问卡片 + 教师批注」，复用现有作业与论坛数据模型，不需要实时连接；
  - 第二步：有后端与账号后，再上 WebSocket 私信，带已读回执与留存期限；
  - 同时定义师生沟通边界（禁止诊断建议、敏感内容提示、教师可导出记录）。
- **触发条件**：有账号体系与服务端存储，且明确合规策略。
- **结论**：不修复

### FB-006 影像缺少专家核验

- **反馈日期**：2026-11-23
- **反馈来源**：真实用户
- **用户原话（整理）**：影像缺少专家核验。
- **现状**：逐区文本与题目由 AI 辅助整理，页面已声明「正式教学前须由医学人员逐条审核签字」，但尚无核验记录与核验状态标识。
- **为什么现在不做**：
  1. 这不是代码问题，需要执业医师 / 影像科医师逐条签字，无法由开发侧代替；
  2. 在没有真实核验前，不能对外宣称「已核验」，只能保持现有边界声明；
  3. 核验一旦开始就需要版本管理（改一条文本就要重新签），流程要先设计。
- **未来方向**：
  - 建立核验工作流：逐条状态（待核 / 已核 / 有异议）+ 核验人 + 日期 + 版本号；
  - 页面显示核验徽标与核验覆盖率，未核验条目明确标注；
  - 先抽检高频考点与高风险表述（如「未见异常」「排除」），再全量；
  - 公开可核验的核验记录，作为答辩材料的一部分。
- **触发条件**：有具备资质的医学审核人并接受逐条签字流程。
- **结论**：不修复
